## Задача 1 — Шапка

### Разведка: причина, а не симптом

Замер на живой странице при 1920 px до правок:

```
headerH: 134          высота шапки
--rz-header-h: 5rem   компенсация = 80px
bodyPadTop: 80px      ->  54 px содержимого уходило под шапку
flexWrap: wrap
дети .rz-header__inner:
  rz-header__brand-link   offsetTop 0    ширина 243
  rz-header__nav          offsetTop 52   ширина 1064
  rz-header__actions      offsetTop 90   ширина 1128
```

Ширина детей и есть причина. Контейнер — 1160 px, а навигация
занимает 1064 и блок действий 1128: каждый почти во всю ширину.
Втроём в строку они не помещаются физически.

Почему они такой ширины: и навигация, и блок действий — это
`core/group`, а в теме есть правило `.wp-block-group { width: 100% }`
(`main.css`, раздел «Раскладка»). Оно и растягивает их.

Пока у контейнера стоял `flex-wrap: nowrap`, это было не видно: флекс
сжимал переросшие элементы обратно. Прошлый прогон разрешил перенос
ради увеличения текста до 200 % — и каждый ребёнок ушёл на свою строку.

**То есть `flex-wrap: wrap` — спусковой крючок, а не причина.**
Это важно: простое возвращение `nowrap` починило бы десктоп и вернуло
горизонтальную прокрутку при 200 % на 375 px. Чинилась ширина.

Ещё две находки разведки:

* фон шапки — `color-mix(… 86%, transparent)` плюс `backdrop-filter:
  blur(10px)`;
* компенсация высоты — `body { padding-top: var(--rz-header-h) }`
  и `html { scroll-padding-top: var(--rz-header-h) }`, то есть обе
  опираются на переменную, а переменная задана числом и с фактической
  высотой никак не связана.

### Что сделано

| Файл | Правка |
|------|--------|
| `main.css` | `.rz-header__inner > .wp-block-group { width: auto }` — дети занимают место по содержимому |
| `main.css` | порог полной навигации 62rem → 65.625rem (1050 px) |
| `main.css` | телефон и кнопка вызова возвращаются с 47.5rem (760 px) отдельным правилом |
| `main.css` | у навигации убраны боковые поля `margin-inline: 2rem` |
| `main.css` | `min-height` шапки переведён на новый токен `--rz-header-min` |
| `main.css` | непрозрачность подложки шапки 86 % → 94 % |
| `tokens.css` | добавлен `--rz-header-min: 5rem` |
| `header.js` | порог `DESKTOP` 62rem → 65.625rem |
| `header.js` | `--rz-header-h` переписывается измеренной высотой шапки |

### Принятые решения

**1. Чинить ширину детей, а не перенос.** Перенос нужен при 200 %
и остаётся разрешённым. После правки ширины при обычном масштабе
содержимое помещается в строку само, и переносу нечего делать.
Оба условия выполняются одним изменением.

**2. Порог полной навигации — 1050 px.** Был 992 px (62rem), и на
1024 px четыре пункта меню, телефон и кнопка в строку уже не
помещались: 932 px содержимого плюс 64 px полей навигации против
992 px колонки. §25 прямо говорит: «Более 1050 px — полная
навигация», «761–1050 px — скрытие части навигации». Порог сдвинут
туда, где ему и место.

**3. Телефон возвращается раньше навигации, с 760 px.** §25 просит
сворачивать на средних ширинах навигацию, §6.1 требует обратного для
телефона: «телефон остаётся видимым на широком экране». Раньше оба
блока показывались одним правилом, и на 1024 px вместе с меню пропадал
телефон — на сайте, где звонок и есть главное действие. Ссылки меню
при этом не теряются: до 1050 px они в мобильной панели.

**4. Высоту шапки меряет скрипт.** Задание требует, чтобы высота жила
в переменной и чтобы компенсация опиралась на ту же переменную —
«чтобы два числа физически не могли разойтись». Пока высота задана
числом, они расходятся при первом же случае, когда шапка окажется
выше задуманного, и этот случай реален: при 200 % на 375 px шапка
занимает 200 px. Поэтому `header.js` переписывает `--rz-header-h`
измеренной высотой. Значение в CSS остаётся запасным: без JavaScript
шапка получает свои 5rem, и для обычного масштаба это верно.

**5. Минимальная высота — отдельный токен.** Первая попытка отдала
`min-height` той же `--rz-header-h`, и получилась петля с храповиком:
скрипт записывал измеренную высоту, она становилась минимальной, шапка
больше не могла стать ниже, и случайный скачок при загрузке застревал
навсегда. Замер показал 100 px на 768 и 96 px на 1050 там, где
содержимому хватало 80. Минимум — величина замысла, измеренная
высота — величина факта; смешивать их нельзя.

**6. Непрозрачность подложки 94 %.** Обоснование — в разделе «Решения
прошлого прогона» ниже.

### Затронутые решения прошлого прогона (инвариант И17)

**Решение 18 прошлого прогона** («перенос в шапке разрешён ради 200 %»)
— **сохранено**. Перенос по-прежнему разрешён, и при 200 % он
по-прежнему срабатывает. Изменена не он, а ширина детей.

**Непрозрачность шапки 86 %** — обоснование прошлого прогона
**заменено**, и вот почему. Там значение выбиралось по контрасту
текста самой шапки: 10.40:1 при 86 % против порога 4.5. Этот замер
верен и сейчас. Но он отвечал не на тот вопрос: читаемость текста
ШАПКИ ничего не говорит о том, просвечивает ли сквозь неё текст
СТРАНИЦЫ.

Замерено иначе — содержимое шапки скрыто, под неё подведена панорама
офиса (самый пёстрый кусок страницы: светлое небо рядом с тёмным
кирпичом), снята полоса шапки, посчитан разброс яркости подложки:

| Непрозрачность | над заголовком | над панорамой |
|----------------|----------------|---------------|
| 86 % (было) | 1.10:1 | **1.28:1 — сквозит** |
| 94 % (стало) | 1.04:1 | 1.10:1 |
| 97 % | — | 1.05:1 |

При 94 % разброс над фотографией такой же, как над обычным светлым
содержимым: кадр перестаёт давать вклад. 97 % убрало бы прозрачность
§6.1 совсем, поэтому взято 94 %.

### Замеры и критерии приёмки

**К1 — одна строка.** Проверка считает строки по пересечению
вертикальных диапазонов детей, а не по равенству `offsetTop`:
контейнер выравнивает детей по центру, и у элементов разной высоты
верхняя кромка законно стоит на разной высоте. `offsetTop` приведён
рядом, как требует задание.

```
  375px z100  строк:1  offsetTop детей: [18,16]
  760px z100  строк:1  offsetTop детей: [28,26]
  768px z100  строк:1  offsetTop детей: [28,26]
 1024px z100  строк:1  offsetTop детей: [18,16]
 1049px z100  строк:1  offsetTop детей: [18,16]
 1050px z100  строк:1  offsetTop детей: [18,25]
 1100px z100  строк:1  offsetTop детей: [18,25]
 1366px z100  строк:1  offsetTop детей: [18,25]
 1920px z100  строк:1  offsetTop детей: [18,25]
```

**К2 — высота и компенсация.** На всех девяти ширинах при 100 %:
высота шапки 80 px, `padding-top` у `body` 80 px. При 200 %:
375 → 200/200, 768 → 334.8/335, 1366 → 192/192. Совпадает везде.

**К3 — заголовки не под шапкой.** Для каждого H1 и H2 страница
прокручивается к нему и в точке верхней кромки выполняется
`elementFromPoint`. Заголовков, накрытых шапкой: **0** на всех
девяти ширинах при 100 % и на трёх при 200 %.

**К4 — 200 % на 375 px.** `scrollWidth` 375, `clientWidth` 375 —
горизонтальной прокрутки нет. Старый дефект не вернулся.

**К5 — бургер.**

```
МЕНЮ 375: до открытия scrollY=500
  открыто: aria-expanded=true aria-controls=rz-menu hidden=false
           overflow=hidden верх панели=80 высота шапки=80
  в панели: ссылок 4, телефон true, режим работы true
  жест колесом: scrollY 500 -> 500 (фон заперт)
  закрыто: aria-expanded=false hidden=true overflow=visible
           scrollY=500 (позиция сохранена) фокус на rz-header__burger
  ошибки: нет
```

**Кнопки §6.1:** шапка 44 px, первый экран 60 px — шапка ниже, верно.

**К6 — скриншоты.** `_reports/shots/before/` и `_reports/shots/after/`,
полной страницей на пяти ширинах. Просмотрены глазами.

*Что изменилось:* на 1366 и 1920 шапка из трёх строк высотой 134 px
стала одной строкой 80 px: слева эмблема с названием, посередине
четыре пункта меню, справа телефон и кнопка «Вызвать специалиста».
Первый экран больше не срезан сверху — панорама начинается сразу под

не изменилась ни на одной ширине (8381 / 7073 / 4877 / 4648 / 4790).
